# JNI artifacts for HugeGraph containers

The `build topling-jni` workflow builds Linux amd64 JNI on Ubuntu 24.04 with
GCC 13. It defaults to `native_features=community`, which consistently sets
`WITH_TOPLING_ROCKS=0 WITH_CSPP_MEMTABLE=0 WITH_TOPLING_DCOMPACT=0` in every Make invocation.
This builds
the public runtime without downloading the optional ToplingZip Builder/CSPP
MemTable trial objects. It always uploads a run-specific
`topling-jni-linux-amd64-<source SHA>`
Actions artifact, including when `deploy_maven=false`. The archive contains:

- `rocksdbjni-8.10.2-linux64.jar` (the version follows `build_tools/version.sh`);
- the JAR's SHA-256 checksum file;
- `build-info.txt`, recording the source revision, build run, compiler, flags and
  the revisions of the SidePlugin repositories used by the build.

The JAR embeds the selected source repositories' license/notice texts under
`META-INF/licenses/`, preserving their source paths. It also includes source-embedded
MIT/BSD notices, the vendored Zstd 1.4.5 BSD license, a license checksum inventory,
and `META-INF/topling-build-info.txt` matching the external build manifest. These
entries are installed before the JAR's final SHA-256 is calculated. The community
preset keeps the public CSPP-WBWI integration. It leaves the public optional
dcompact integration disabled for a smaller runtime; dcompact is separate from
the proprietary CSPP MemTable and ToplingZip Builder components.

Community plugin revisions are fixed in
[`community-jni-sources.json`](../.github/community-jni-sources.json) to the source
set validated by the published `jni-2916f6895c62e535a03985d8e9b0879e64304715` artifact.
CI checks out those commits before invoking Make, initializes their pinned
submodules, and verifies clean source revisions before compiling and packaging.
Before compilation, all tracked changes and untracked inputs are rejected,
including files hidden by `.gitignore`, `.git/info/exclude` or `core.excludesFile`.
Only the known generated `build/` and `build-ut/` directories are excluded from
this check. A successful check writes a clean-start receipt bound to the source
revision, locked source set, Actions run and attempt. Existing dirty checkouts
are rejected without deleting their files.

The pinned dependencies also generate 14 files in their source directories.
After compilation, `verify-built` requires that matching clean-start receipt,
rechecks commits and tracked files, and permits only these exact extra outputs:

- topling-zip's `3rdparty/base64/lib/config.h`, `codec_choose.o`, `lib.o` and
  `libbase64.o`, plus `arch/{avx,avx2,generic,neon32,neon64,sse41,sse42,ssse3}/codec.o`
  under the same `lib/` directory, generated by its pinned base64 Makefile;
- Boost's `libs/config/checks/architecture/bin/gcc-13/debug/64.o` and `x86.o`,
  generated by the pinned Boost architecture checks.

Their SHA-256 values and source paths are recorded in build provenance. These
paths are never exempted before compilation; pre-existing ignored configuration
or object files still fail the clean-start check. No general `.o`, `.h`, source
directory or ignore-rule exemption is applied after compilation. The pinned
Makefiles provide no common output-directory override for these files; moving
them would require changing external source rather than merely locking it.
`UPDATE_REPO=0` prevents Make from pulling newer branches; it alone does not stop
automatic clones of missing repositories, which is why CI prepares every enabled
public plugin first. The lock includes Boost's gitlink; RapidYAML/c4core are
vendored within the pinned rockside tree. Build provenance records the lock's
SHA-256 and every verified revision. A private `topling-core` checkout is rejected
because the Makefile would select it ahead of the public runtime. Optional
filesystem integration is explicitly disabled in this container workflow.

To update a community plugin, review its commit and matching licenses, update the
lock (and the parent gitlink for a submodule), then run the JNI and container
checks before changing an image's pinned JAR URL/checksum. Pinning the existing
source set does not replace or alter the already published artifact. Source and
trial-binary pinning for the optional full feature preset remains separate work;
it does not use the community lock.

The build enables `ROCKSDB_DYNAMIC_CREATE_CF`, required by HugeGraph backend
initialization. Before upload, the workflow loads the native JNI, applies a configuration through
`TOPLINGDB_EASY_MIGRATE_CONF`, creates a column family, writes to both column
families in a disposable database and reopens them. It checks
that the configured write-buffer size was persisted. This is a runtime capability
check; it does not certify existing database migration or every production option.

For a public download suitable for Docker builds, manually dispatch the workflow
on the desired source ref with `publish_release=true`. Maven publication is
independent and can be disabled. After the complete build passes, a separate job
publishes the same verified payload under the tag `jni-<full source SHA>`:

```text
https://github.com/hugegraph/toplingdb/releases/download/jni-<full source SHA>/rocksdbjni-8.10.2-linux64.jar
```

Create that release tag before dispatching a publication. The workflow
token has `contents: write` but cannot create a new tag targeting a commit that
changes workflow files; pre-creating the tag with the maintainer's normal Git
credentials lets the publication job use the existing tag without broader token
permissions. The job resolves the remote tag, including annotated tags, and
requires its commit to equal the build's `SOURCE_SHA` before creating a release.
`--verify-tag` alone checks existence and cannot establish this match. This
workflow never replaces an existing release. That is not repository-enforced
release immutability: another authorized writer can still change or remove tags
and assets. A pinned checksum rejects changed bytes, but cannot guarantee that
the download URL remains available.

Pin the JAR URL and its SHA-256 in reviewed configuration, independently of the
downloaded files; HugeGraph's `docker/topling-runtime.env` is the consumer's
reviewed pin. For the approved `jni-2916f6895c62e535a03985d8e9b0879e64304715`
community artifact, verify the trusted digest directly:

```bash
TOPLING_JNI_SHA256='c9066873d5eb38585517c0c4065565897aab96629585731b6fb36d64b81efef2'
printf '%s  %s\n' "$TOPLING_JNI_SHA256" 'rocksdbjni-8.10.2-linux64.jar' | sha256sum --check
```

For another approved artifact, update the URL and digest together through the
same review process. The sibling `.sha256` file is a convenient transfer check;
it is not an independent trust anchor when downloaded beside the JAR. Avoid
moving branch URLs and Maven snapshot metadata.

Alternatively, push a `jni-build-*` tag pointing to a reviewed source commit. This
triggers the same community build and publishes its `jni-<source SHA>` release,
which this workflow refuses to replace. Publication happens
release after the JNI checks pass; Maven publication and JMH remain disabled:

```bash
source_sha="$(git rev-parse HEAD)"
git tag "jni-${source_sha}" "$source_sha"
git tag "jni-build-${source_sha}" "$source_sha"
git push origin "jni-${source_sha}" "jni-build-${source_sha}"
```

The manual `native_features=full` choice requests optional ToplingZip Builder/CSPP
MemTable trial components and public optional dcompact integration. It is an
experimental build-only mode: explicitly set both `deploy_maven=false` and
`publish_release=false`. Maven and release publication of full candidates fail
closed until the private integrations are qualified. The manifest records the
requested flags and marks full candidates `experimental_unqualified`; those
flags alone are not evidence that integrations were linked or accepted.

Full candidates must load the final JNI and create the registered `DcompactCmd`
factory through `SidePluginRepo`. This catches a missing dcompact clone even
when Make swallowed the clone failure. The probe does not execute a command,
start a worker or test remote compaction. It also does not qualify the private
CSPP memtable or ToplingZip builder: that requires their actual selection,
writes, forced flush/restart and persisted SST-type checks. Creating a generic
ToplingZip factory can fall back to a public reader and is insufficient.
No full native acceptance run is claimed by this PR.

Use a configuration matching the selected features. Community images use public
SkipList/BlockBasedTable factories; CSPP configurations require a separately
qualified and appropriately licensed supplier artifact. The manifest and bundled
notices do not extend any trial license. The published community default remains
the real `jni-2916f6895c62e535a03985d8e9b0879e64304715` binary; merging newer source
or adding these guards does not change its source revision or checksum. New
native builds and the new workflow integration remain pending validation.

The current native runtime is Linux amd64
and requires an AVX2/BMI2-capable CPU, glibc 2.38 or newer, and its native runtime
dependencies. Use HugeGraph's `prepare-topling.sh` on the final image base to verify
the JAR checksum, ELF architecture, native dependencies and Java 17 configuration
entry point before publishing an image. On Ubuntu, the preparation script handles
the libaio t64 soname within the prepared runtime directory.
